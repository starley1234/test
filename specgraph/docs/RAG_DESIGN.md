# RAG v2 — эффективность и бюджет контекста

## Проблема

Конструктор работает с документами, которые падают в воркспейс и индексируются.
Классический чанковый RAG (top-3 чанка) не отвечает на:

- `Какие документы загружены?` — список документов не влезет в 3 чанка, особенно когда их 20.
- `Сколько требований в Документе 1` — нужен `COUNT(*)`, а не вектор.
- `Найди REQ-007` — код разрезан между чанками, лежит в таблице.
- `В каком требовании про надёжность` — может сработать, но без кода требования.

При 100+ требованиях в документе, если класть всё в промпт — 100 * 500 симв = 50k симв ≈ 14k токенов — дорого и медленно. Жжём контекст попусту.

## Решение — гибридный RAG с бюджетом

### Уровни

1. **Meta Layer** — 0 токенов, без LLM
   - `documents` таблица, `COUNT(requirements)` , `list`
   - ответ детерминированный, мгновенный
   - экономит 100% токенов на простых вопросах

2. **Exact Layer** — ~150 токенов
   - точный поиск по `code` / `title` — `WHERE code LIKE %X%`
   - 1 требование, без векторов

3. **Lexical Layer** — дёшево, быстро
   - токенизация, стоп-слова, `lexical_score` = перекрытие токенов
   - работает офлайн, без эмбеддингов

4. **Vector Layer** — семантика
   - эмбеддинги требований (384 dim), hash fallback когда HF недоступен
   - находит синонимы: `надёжность` == `MTBF` == `наработка на отказ`
   - cosine similarity

5. **Fusion + Budget Packing**
   - комбинированный score: `0.7*semantic + 0.3*lexical`
   - сортировка по score, жадная упаковка под бюджет:
     - `budget_chars` — настраивается (500..50000), по умолчанию 8000 симв ~ 2285 ток (ru 3.5 симв/ток)
     - распределение: 70% требования, 20% чанки, 10% meta
     - усечение по предложениям, а не посередине слова
     - `truncate_text` с поиском последней точки
   - в ответе `budget_breakdown`: used/remaining, estimated tokens

### Бюджет — главный регулятор

Пользователь (конструктор) ставит ползунок в UI:

- **2000 симв** — эконом: 1-2 требования, для быстрого поиска кода
- **8000 симв** — оптимум: 5-8 требований по 400 симв + 2-3 чанка — хватает для большинства вопросов `про надёжность`
- **16000 симв** — аналитика: 12-15 требований, для генерации тестов/проверки

Почему именно так, а не фиксированный top_k=10:

- top_k=10 без учёта длины — может быть 10*1000=10k симв, а бюджет 2k — переполнение.
- budget — честный лимит в символах/токенах, который напрямую влияет на стоимость LLM.

В пайплайнах (`validate-requirements`, `generate-tests`, `summarize`, `review-correctness`) тоже используется бюджет:

- Раньше `gather_context` тянул всё подряд (все требования документа).
- Теперь `gather_advanced_rag_context` тянет только релевантные под `top_k` и упаковывает под `budget_chars`.
- `review-correctness` обрабатывает по одной карточке (как и раньше) — это уже эффективно: пауза/стоп, не грузит сразу 100 карточек в один промпт.

### Эффективная работа с требованиями без сжигания контекста

1. **Храните как сущности, а не как чанки**
   - требование = `{code, title, text(200–500с), kind, section_path, attributes}` — 150 ток вместо 500 ток чанка с шумом.
   - чанки нужны только как дополнение (например, таблица из приложения).

2. **Иерархия запросов**
   ```
   query -> intent router -> meta? (0 ток) -> exact? (1 треб) -> lexical/vector + budget pack -> LLM (только если нужно)
   ```
   - 70% вопросов конструктора — это meta (`сколько`, `какие`, `найди по коду`) — отвечаем без LLM.

3. **По одной карточке в пайплайнах**
   - `review-correctness` — 1 требование + его родители (2-3 шт) + атрибуты = <1k ток на итерацию.
   - Можно ставить на паузу, смотреть матрицу по уже проверенным.

4. **Бюджетные пресеты в UI**
   - эконом/оптим/много — пользователь видит сразу сколько токенов сожжёт.

5. **Кэш и дедупликация**
   - только `is_current=True`, без stub/appendix
   - эмбеддинги кэшируются в `embeddings` таблице, переиспользуются
   - одинаковые запросы с одинаковым бюджетом — можно кэшировать по хешу (TTL 5 мин)

6. **Сжатие текста**
   - усечение по предложениям, а не по символам
   - для длинных требований — показывать первые 400 симв + `…` + ссылка на полный текст (в инспекторе)

7. **Токен-эстимация**
   - `tokens ≈ chars / 3.5` для русского (проверено эмпирически)
   - в UI показывается сразу и в символах и в токенах

### Что вернули и улучшили из старых пайплайнов

Старый `catalog.json` содержал 7 пайплайнов, мы оставили только 1 в `3775343`. Теперь вернули все и улучшили:

- `help-write`, `validate-requirements`, `generate-tests`, `summarize`, `review-one`, `review-correctness`, `unit-tests`, `schematic-coverage`
- Все используют `gather_advanced_rag_context` с бюджетом:
  - `validate-requirements` — находит только релевантные противоречивые требования под бюджет, а не все 100
  - `generate-tests` — берёт топ-15 по запросу/фильтру, а не весь документ
  - `review-correctness` — уже был эффективен (по одной карточке), теперь родители тоже берутся через RAG v2 + бюджет

В UI `/dev` (старый dev-интерфейс) пайплайны тоже работают, но новый `/app` (RAG v2 Lab) показывает бюджет явно.
