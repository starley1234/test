# Модель сущностей

Документ ТЗ/ТУ/спецификации — не «текст для RAG», а **два дерева + рёбра**.

```
Document
 ├── Product (изделие) ──parent──► Product
 │     └── ProductAttribute (масса, питание, интерфейс…)
 ├── Requirement ──parent──► Requirement (уточнение)
 │     └── RequirementAttribute (верификация, приоритет, статус)
 └── Illustration (Tika / word/media) ──caption──► Product
```

## Почему так

1. **Изделие с атрибутами** — объект испытаний и проектирования. Иерархия = состав (система → модуль → плата). Без неё требование «наработка ЦП 10 000 ч» нельзя привязать к правильному узлу.
2. **Требование с атрибутами** — атомарное shall/должен. Иерархия = декомпозиция (ТР-4.1 → ТР-4.1.1). Атрибуты верификации нужны пайплайну генерации тестов.
3. **Связи отдельно от FK** (`EntityRelation`) — чтобы тянуть подграф любого типа: `applies_to`, `composed_of`, `refines`, `depends_on`, `illustrated_by`, `conflicts_with`.
4. **Иллюстрации** — в текстовом дампе Word их нет. Канал: OOXML `word/media` + Apache Tika для `.doc`/`.docm`. Подпись «Рисунок N — …» линкуется на изделие по коду/имени.
5. **Эмбеддинги** — не вместо графа, а вход в него: семантический hit → раскрытие соседей на `hop` шагов.

## Контекст для пайплайна

`POST /retrieval/context` возвращает:

- seed (изделие / требование / запрос);
- предков и потомков изделия;
- требования на этом срезе + атрибуты;
- иллюстрации;
- типизированные рёбра;
- top-k семантических попаданий.

LangGraph: `retrieve → reason → pack`. Новые пайплайны — новый system-prompt на том же retrieve.
